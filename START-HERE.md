# Start here

Use this repository to build an original LitRPG novel or improve an existing one. Follow the owner's current request; the playbook supplies a method, not a competing story vision.

When no mode is specified, use guided mode for planning and complete one step. An explicit request for a complete chapter, episode, batch, or book selects execution for that scope, including necessary checks and revisions.

## Reading order for an assistant

1. Read this file, [PROMPT.md](PROMPT.md), [STYLE.md](STYLE.md), and the relevant step in [PLAYBOOK.md](PLAYBOOK.md).
2. Read [FINDINGS.md](FINDINGS.md) and [SOURCES.md](SOURCES.md) to understand the synthesis and its limits. Follow the linked research note when using a particular author's advice or making a source-specific claim.
3. Read the relevant reference: [System](SYSTEM-DESIGN.md), [world and characters](WORLD-AND-CHARACTERS.md), [pacing](PACING-AND-PROGRESSION.md), [examples](EXAMPLES.md), [continuity](CONTINUITY.md), or [revision](REVISION.md). Use the continuity method in Steps 3, 5, and 8–11. Do not pretend that opening this file loaded the entire repository.
4. For an existing project, read its authoritative story registry, approved style, current manuscript, and handoff. Before every next chapter/episode, open and read the same persistent Excel workbook: latest confirmed actual ending, resources, knowledge, injuries, rule versions, stopping point, review status, and blocking issues. Resolve blockers, then retrieve chapter-appropriate information for drafting. Keep future revelations away from the drafting worker and simulated reader.
5. Name the current step, produce its requested artifact, check its completion criteria, and record the next useful action. In guided mode stop for the owner's review after the step. In execution mode complete the whole requested piece and ordinary fixes.

## If the owner supplied only this link

Ask: **What kind of LitRPG story do you want to build?**

If an idea was supplied, begin Step 1. Ask only about missing information that would materially change the result; offer sensible defaults. Do not require a questionnaire about every possible world detail.

## Useful commands

- **Start Step 1:** turn my idea into a one-page brief.
- **Continue the next step:** use my latest approved project state.
- **Revise Step 3:** change the System and trace every affected plot and progression decision.
- **Draft Chapter 1:** use the approved brief, rules, and chapter card; finish the prose and revision.
- **Audit this chapter:** report and fix clear inconsistencies within the authorized scope.
- **Prepare Pocket FM adaptation:** use Step 12 after the underlying story decisions are settled.

## What must persist in the project

Use [templates/PROJECT.md](templates/PROJECT.md) as the project's `story.md` registry. It points to the current brief, style, characters, System, world, outline, chapters, and continuity. Keep one authoritative version of each fact. A small project may use sections in a single file; a novel may split them into linked files.

Keep brainstorms separate from approved facts. A helpful proposal does not become established canon merely because an assistant wrote it. Record chapter changes only after reading the final prose. The handoff points to the authoritative records; it is not a second story bible.

Use the required per-episode loop in [CONTINUITY.md](CONTINUITY.md), including when one novel chapter contains several episodes. After full prose, revision, and a final read, update that same workbook's existing sheets with confirmed actual facts, final source/version or hash, affected checks, stopping point, and review status. Verify the saved records before starting the next episode. Preserve prior history and notes; do not create a new workbook or sheets per episode. For a new project with no workbook, create one from approved opening conditions before Episode 1. Report an inaccessible existing workbook and resolve access before dependent drafting. Keep plans separate from final-text evidence. An authorized GitHub mirror updates the same paths in place; it is not a second canon or a complete brief for a bounded writer or reader.

## When access or knowledge is missing

Say what could actually be read. Ask for inaccessible project facts when necessary, or produce an explicitly provisional option. Never invent a source reading, a saved file, completed audio listening, owner approval, or publication state. If the browser cannot reach GitHub, request the relevant file contents; do not claim the link worked.
